1What you'll build

On the robot, the main controller talks to the motors, the gimbal and the other boards over CAN. Before you touch a real robot, you'll learn CAN on three simulated RoboMaster Development Board Type A (“Dev-A”, STM32F427IIH6) boards.

Each board runs the same firmware. The only difference is a number, NODE_ID (1, 2 or 3). When you've finished the four tasks in chapter 6, every board:

  1. sends a small heartbeat frame on the bus at its own period, and
  2. prints every frame it receives on its serial port (USART6) and shows a counter from the frame in binary on its 8 LEDs.
BoardCAN ID it sendsPeriodData bytes
node10x101500 ms01, counter
node20x102600 ms02, counter
node30x103700 ms03, counter

Why a simulator?

Renode is an open-source simulator from Antmicro. It runs the exact .elf file you would flash onto a board, with the CPU, timers, GPIO, UART and CAN controller emulated. You can run three boards, connect them to one virtual bus and watch every frame without wiring anything or bricking a board.

Keep in mind

A simulator is not the real thing. Renode does not simulate wiring, pin choice, bit timing or bus errors. Chapter 9 lists exactly what changes on real boards. Read it before your first hardware session.

2CAN in ten minutes

2.1 One pair of wires, many boards

A CAN bus is two wires, CAN_H and CAN_L, usually twisted together. Every board connects to the same two wires, in parallel. A 120 Ω resistor at each end of the bus stops signals from reflecting back.

The bus only has two states:

  • Dominant = logic 0. A transmitter pushes CAN_H up and CAN_L down.
  • Recessive = logic 1. Nobody drives the bus; the resistors pull CAN_H and CAN_L to the same voltage.

If any one board sends a 0, the whole bus reads 0. “0 wins” is the most important rule in CAN; it makes arbitration and ACK work (see 2.5 and 2.6).

Because the receiver looks at the difference between the two wires, noise that hits both wires equally cancels out. That's why CAN survives next to motors.

2.2 Inside each board

  • The CAN controller lives inside the microcontroller. On the STM32F4 it's called bxCAN (there are two: CAN1 and CAN2). It builds frames, handles timing, CRC, ACK and retries, and filters incoming frames. Your code only ever talks to the controller, through the HAL.
  • The transceiver is a separate chip (an MCP2562 on the Dev-A). It converts the controller's TX/RX logic pins into CAN_H/CAN_L voltages and back.

bxCAN has 3 transmit mailboxes (frames waiting to go out), 2 receive FIFOs that hold 3 frames each, and 28 filter banks shared between CAN1 and CAN2.

2.4 Everyone hears everything

CAN has no addresses. When a board sends a frame, every other board on the bus receives it. The ID tells receivers what the message is about; each receiver decides whether it cares. The CAN controller can do that sorting in hardware with filters, so your code never sees frames it doesn't want. A board never receives its own frames.

2.5 IDs are priorities: arbitration

What if two boards start sending at the same moment? Both send their ID bit by bit, most significant bit first, and both listen to the bus while they send. Because 0 wins, as soon as one board sends a 1 but reads back a 0, it knows someone with a lower ID is also sending. It stops and tries again after the bus is free. The winner never notices and no data is lost.

Bit109876543210
node1 sends 0x10100100000001
node2 sends 0x1020010000001 ✗
bus00100000001

The lower the ID, the higher the priority. That's why DJI motor commands use ID 0x200 and the motors' feedback uses 0x201 and up.

2.6 ACK: somebody has to answer

In the ACK slot of every frame the sender transmits a 1, and every receiver that got the frame correctly overwrites it with a 0. If the sender reads back a 1, nobody received the frame. It reports an error and sends again, forever.

Common first-day bug

A board alone on the bus never gets an ACK, so its 3 transmit mailboxes fill up and stay full. Same if the other board isn't running, or uses a different bit rate. In Task 3 you'll make your firmware print tx skipped: all 3 mailboxes busy when that happens.

2.7 Bit rate and bit timing

All boards on a bus must use the same bit rate. RoboMaster robots use 1 Mbit/s, the rate DJI motors and ESCs expect. The controller splits each bit into small time slices called time quanta (tq) and reads the bus at the sample point, near the end of the bit:

You'll see how these numbers are set in code in section 5.3.

4First run: the starter project

The project you cloned is a starter. Everything CubeMX would generate is done: clocks, pins, the CAN1 bit rate, the serial port, printf. Four small functions are left empty for you. Before you write anything, build and run it so you know what “nothing done yet” looks like.

  1. Build the firmware. From the repository folder: 
    make
    This compiles the same code three times, once with -DNODE_ID=1, once with 2 and once with 3, and ends with: 
    LD  build/node3.elf
   text    data     bss     dec     hex filename
  11632     112    2312   14056    36e8 build/node3.elf
    You now have build/node1.elf, node2.elf and node3.elf: one file per board. Run make again and it says Nothing to be done: it only rebuilds files that changed.
  2. Start the simulation. 
    make sim
    Renode loads sim/can_bus.resc, which creates three Dev-A boards, loads one .elf into each, connects all three CAN1 controllers to one virtual bus, and starts them. The first run downloads a small register-description file, so you need internet.
  3. Look at the output. After a few seconds: 
    node1/usart6: [… virt: 0.1ms …] [node1] up: sending id=0x101 every 500 ms
node2/usart6: [… virt: 0.1ms …] [node2] up: sending id=0x102 every 600 ms
node3/usart6: [… virt: 0.1ms …] [node3] up: sending id=0x103 every 700 ms
    And then nothing. The boards boot and announce themselves, but nobody sends anything yet: that's your job.
  4. Stop it. Type quit and press Enter (the prompt shows (node3)), or press Ctrl+C.
  5. Run the automatic check. 
    make test
    Every test fails, because no task is done yet. Each one is named after the task it checks, so as you work through chapter 6 you'll see them turn OK one by one. (On a Mac, chapter 8 shows a one-time setup step for make test.)

Here is the main loop, so you can see where your functions get called:

while (1)
{
  /* Every HEARTBEAT_PERIOD_MS milliseconds, send one heartbeat. */
  if ((int32_t)(HAL_GetTick() - next_tx) >= 0)
  {
    next_tx += HEARTBEAT_PERIOD_MS;
    send_heartbeat(counter++);                  /* ← Task 3 */
  }

  /* Print every frame the receive callback has queued up. */
  RxFrame f;
  while (rx_pop(&f))                            /* ← filled by Task 4 */
  {
    print_rx(&f.header, f.data);
    if (f.header.DLC >= 2)
    {
      show_on_leds(f.data[1]);                  /* ← Task 1 */
    }
  }
}

HAL_GetTick() counts milliseconds since boot. Writing the timer check as a subtraction keeps it working when the 32-bit counter wraps around after 49 days.

HAL_CAN_Init() leaves the controller in initialization mode: configured, but off the bus. Joining the bus is Task 2.

Pins and the interrupt

HAL_CAN_Init() calls HAL_CAN_MspInit() in stm32f4xx_hal_msp.c, which puts CAN1 on PD0 (RX, with a pull-up) and PD1 (TX). Those come from the Dev-A schematic, not CubeMX's default of PA11/PA12. It also enables the CAN1_RX0 interrupt in the NVIC. When that interrupt fires, CAN1_RX0_IRQHandler() in stm32f4xx_it.c calls HAL_CAN_IRQHandler(&hcan1), which works out why and calls your Task 4 callback.

printf

printf() doesn't know about UARTs. The C library calls _write() to output characters, and main.c provides one that sends them out of USART6. In the simulator, Renode prints whatever arrives on USART6 into its log.

Task 1: LEDs (GPIO warm-up)

Goal: show_on_leds(value) shows value in binary on the 8 user LEDs, LED_A = bit 0 up to LED_H = bit 7. main() calls it at boot with NODE_ID, so node3 should light LED_A and LED_B (3 = 00000011).

You'll use: HAL_GPIO_WritePin(port, pin, state), LED_GPIO_Port, LED_A_Pin…LED_H_Pin.

What you need to know

  • The LEDs are active-low. On the Dev-A each LED sits between 3.3 V (through a 1 kΩ resistor) and its pin. Current only flows when the pin is low, so GPIO_PIN_RESET turns an LED on and GPIO_PIN_SET turns it off.
  • Pins are bit masks. LED_A_Pin is GPIO_PIN_1, which is just the number 1 << 1; LED_B_Pin is 1 << 2, and so on. Because the 8 LEDs are on neighbouring pins (PG1–PG8), LED_A_Pin << n is the pin for LED number n.
  • Reading one bit. In C, (x >> n) & 1 is bit n of x. Example: 6 is 110 in binary, so (6 >> 0) & 1 is 0 and (6 >> 1) & 1 is 1.

Steps

  1. Loop over the 8 bits.
  2. For each bit, decide on or off, and remember the LEDs are active-low.
  3. Write that state to the matching pin with HAL_GPIO_WritePin().

Check

The log doesn't change, so look at the LEDs (section 4, “Peek at the LEDs”). On node3, gpioPortG.led_a State and led_b should print True and led_c False. Then make test: Task 1 - LEDs Show NODE_ID At Boot should be OK.

Common mistakes
  • Everything is backwards (node3 lights LED_C to LED_H): you forgot the LEDs are active-low.
  • Only LED_A ever changes: you wrote to LED_A_Pin every time instead of shifting it.

Task 2: Start CAN1

Goal: can_start() brings CAN1 onto the bus, ready to accept every frame into receive FIFO0.

You'll use: CAN_FilterTypeDef, HAL_CAN_ConfigFilter(), HAL_CAN_Start(), Error_Handler().

What you need to know

  • After MX_CAN1_Init(), CAN1 knows its bit rate but is still in initialization mode: off the bus.
  • Until at least one filter is active, bxCAN throws every received frame away. A filter decides which IDs to keep and which FIFO they go into.
  • In mask mode a filter has an ID and a mask. For every mask bit that is 1, the received ID bit must equal the filter's ID bit; mask bits that are 0 mean “don't care”. So a mask of all zeros means “don't care about anything”: every frame is accepted.

Steps

  1. Make a CAN_FilterTypeDef (start it with = {0}) and fill in every field from the table in section 5.4: bank 0, mask mode, 32-bit scale, ID and mask all zero, FIFO0, enabled, SlaveStartFilterBank = 14.
  2. Call HAL_CAN_ConfigFilter(&hcan1, &filter). If it doesn't return HAL_OK, call Error_Handler().
  3. Call HAL_CAN_Start(&hcan1), with the same check.

Check

Still nothing new in the log, because nothing is being sent yet. make test: Task 2 - CAN1 Is Started With A Filter should be OK. That test reads two CAN1 registers directly: CAN_MCR (has the controller left initialization mode?) and CAN_FA1R (is filter bank 0 active?).

Common mistakes
  • The up: lines don't appear any more: the board stopped in Error_Handler() before printing, because one of your calls didn't return HAL_OK. Check the filter fields.
  • make test says CAN1 is still in initialization mode: HAL_CAN_Start() isn't being called, or you return before reaching it.

Task 3: Send a frame

Goal: send_heartbeat(counter) sends one frame with ID HEARTBEAT_ID and 2 data bytes: NODE_ID, then counter. main() already calls it on a timer.

You'll use: CAN_TxHeaderTypeDef, HAL_CAN_AddTxMessage(), HAL_CAN_GetTxMailboxesFreeLevel(), print_tx().

What you need to know

  • The header describes the frame: StdId, IDE, RTR, DLC (section 2.3 shows where each sits in a frame). The data is a separate uint8_t array.
  • HAL_CAN_AddTxMessage() doesn't wait for the frame to go out. It puts it in one of 3 transmit mailboxes and returns; the controller sends it as soon as the bus is free and retries on its own if needed. Its last argument is the address of a uint32_t where it writes which mailbox it used.
  • On a real bus, if nobody acknowledges your frames (2.6), they stay in the mailboxes and all 3 fill up. Checking HAL_CAN_GetTxMailboxesFreeLevel() first lets you print a clear message instead of failing silently.

Steps

  1. Make a CAN_TxHeaderTypeDef and set StdId, IDE, RTR, DLC and TransmitGlobalTime.
  2. Make a 2-byte uint8_t array with NODE_ID and counter.
  3. If no mailbox is free, print tx skipped: all 3 mailboxes busy and return.
  4. Call HAL_CAN_AddTxMessage(). If it returns HAL_OK, call print_tx(&header, data); otherwise print that it failed.

Check

make sim now shows every board sending, on its own period:

[node1] tx id=0x101 dlc=2 data: 01 00
[node2] tx id=0x102 dlc=2 data: 02 00
[node3] tx id=0x103 dlc=2 data: 03 00
[node1] tx id=0x101 dlc=2 data: 01 01
[node2] tx id=0x102 dlc=2 data: 02 01

There are no rx lines yet. The frames reach the other boards' FIFOs, but nothing reads them out: that's Task 4. make test: Task 3 - Each Node Sends Its Heartbeat should be OK. That test watches the bus itself, not the log.

Common mistakes
  • Every send prints “failed”: Task 2 isn't working, so the controller isn't on the bus.
  • The test complains about the length: DLC must be 2, the number of data bytes.
  • The data shows 00 00: you passed an empty array, or the wrong variable.

Task 4: Receive frames

Goal: every frame another board sends is printed as an rx line and shown on the LEDs.

You'll use: HAL_CAN_ActivateNotification(), HAL_CAN_GetRxMessage(), CAN_RxHeaderTypeDef, rx_push().

What you need to know

  • An interrupt pauses main() wherever it is, runs a handler, then carries on. The HAL turns the CAN1 RX0 interrupt into a call to HAL_CAN_RxFifo0MsgPendingCallback(). You don't call this function yourself; the HAL does, every time a frame lands in FIFO0.
  • Keep interrupt code short. Printing a 40-character line at 115200 baud takes about 3.5 ms, and other interrupts wait meanwhile; on a robot that could mean missed motor feedback. So the callback only copies the frame into a queue with rx_push(), and the main loop prints it later.
  • The interrupt keeps firing while FIFO0 is not empty. If the callback doesn't call HAL_CAN_GetRxMessage(), the frame stays there, the interrupt fires again straight away, and the board is stuck in it forever. That's why you write part B before part A.

Steps

  1. Part B, the callback. In HAL_CAN_RxFifo0MsgPendingCallback(), make a CAN_RxHeaderTypeDef and a uint8_t data[8], call HAL_CAN_GetRxMessage(hcan, CAN_RX_FIFO0, &header, data), and if it returns HAL_OK, call rx_push(&header, data). Use the hcan parameter, not &hcan1; it's the same handle, but this is how HAL callbacks are written.
  2. Part A, the switch. At the end of can_start(), call HAL_CAN_ActivateNotification(&hcan1, CAN_IT_RX_FIFO0_MSG_PENDING), with the usual HAL_OK check.

Check

[node1] tx id=0x101 dlc=2 data: 01 00
[node2] rx id=0x101 dlc=2 data: 01 00
[node3] rx id=0x101 dlc=2 data: 01 00
[node2] tx id=0x102 dlc=2 data: 02 00
[node1] rx id=0x102 dlc=2 data: 02 00
[node3] rx id=0x102 dlc=2 data: 02 00

Every frame is received by both other boards and never by its sender. That's CAN broadcasting (2.4). The LEDs now show the counter of the last frame received. make test: all five tests OK, ending with Tests finished successfully :).

Common mistakes
  • node2 and node3 stop after 0.5 s and only node1 keeps sending: you turned the interrupt on (part A) but the callback doesn't read the frame out. node2 and node3 are stuck re-entering the interrupt.
  • tx lines but no rx lines: part A is missing, or the callback's name is misspelled. It must be exactly HAL_CAN_RxFifo0MsgPendingCallback, or the HAL calls its own empty version instead.
Done!

You've configured a CAN controller, sent frames, and received them through an interrupt, the same steps that talk to every motor and board on the robot. Commit your work, then try the challenges.

7Challenges

Optional, once all four tasks pass. These change what's on the bus, so some automatic tests will fail afterwards; that's expected. Commit your working Task 4 first so you can get back to it.

Challenge 1: Send a 16-bit number

Make each heartbeat 4 bytes long. Bytes 2 and 3 hold a 16-bit value, NODE_ID × 1000 + counter, high byte first (“big-endian”, the order DJI motors use). Receivers print the decoded value.

  • value >> 8 is the high byte and value & 0xFF the low byte.
  • To rebuild it: (data[2] << 8) | data[3]. You'll need to add a line to print_rx() or to the main loop.
[node1] tx id=0x101 dlc=4 data: 01 00 03 E8
[node2] rx id=0x101 dlc=4 data: 01 00 03 E8  -> value=1000
[node2] tx id=0x102 dlc=4 data: 02 00 07 D0
[node1] rx id=0x102 dlc=4 data: 02 00 07 D0  -> value=2000

Think about it: 1000 is 0x03E8. What would the receiver print if it got the byte order backwards?

Challenge 2: Filters

Make every board accept only ID 0x101. Change only the filter in can_start().

In 32-bit mask mode the 11-bit standard ID sits in the top 11 bits of the 32-bit filter register:

Register bits31 … 2120 … 3210
MeaningSTID[10:0], the standard IDEXID (extended IDs only)IDERTR0
HAL fieldFilterIdHigh holds bits 31…16 and FilterIdLow holds bits 15…0, so the standard ID lands in bits 15…5 of FilterIdHigh.

Expected: node1 receives nothing (it never hears itself, and only 0x101 is allowed), and node2 and node3 receive only 0x101.

[node1] tx id=0x101 dlc=2 data: 01 00
[node2] rx id=0x101 dlc=2 data: 01 00
[node3] rx id=0x101 dlc=2 data: 01 00
[node2] tx id=0x102 dlc=2 data: 02 00
[node3] tx id=0x103 dlc=2 data: 03 00

Think about it: which mask accepts both 0x102 and 0x103 but nothing else? (They differ only in bit 0.)

Challenge 3: A DJI-style motor command

DJI's C620 motor controllers listen for ID 0x200: 8 bytes holding four signed 16-bit current commands, for motors 1 to 4, each high byte first (Appendix A).

  • node1 is the “main controller”: right after each heartbeat it also sends ID 0x200 with 1000, -1000, 0, 0. Write a send_motor_command(int16_t m1, int16_t m2, int16_t m3, int16_t m4) and call it only when NODE_ID == 1.
  • node2 pretends to be motor 1 (bytes 0–1) and node3 motor 2 (bytes 2–3). In the main loop, when a frame with ID 0x200 arrives, each decodes its own two bytes into an int16_t and prints it.
[node2] rx id=0x200 dlc=8 data: 03 E8 FC 18 00 00 00 00
[node3] rx id=0x200 dlc=8 data: 03 E8 FC 18 00 00 00 00
[node2] my current command = 1000
[node3] my current command = -1000

Think about it: −1000 arrives as FC 18. Why? (Look up “two's complement”.) And why do the LEDs suddenly show 11101000 after a 0x200 frame?

9From the simulator to real boards

9.1 What the simulator does not check

Renode models CAN at the level of whole frames. Several things that break real buses are invisible in the simulator:

On real hardwareIn Renode
CAN1 must be on PD0/PD1 (the pins wired to the transceiver)Pin choice is ignored. PA11/PA12 would “work” too.
CAN1_RX needs a pull-upNot modeled
All boards must use the same bit rateBit timing is stored but ignored. A board at 500 kbit/s still “works”.
Someone must ACK; errors, retries and bus-off happenEvery frame succeeds instantly, even with no other board.
Arbitration takes time; a busy bus delays framesFrames are delivered instantly, no contention.
Wiring, termination, loose connectors, noiseNot modeled

The repository also works around one Renode quirk: ST's HAL_CAN_Init() requests initialization mode while the controller is still asleep, which real bxCAN allows and Renode's model didn't. A one-line hook in sim/dev-a.repl fixes that. You don't need it on hardware.

9.2 What you need

  • 2 or 3 Dev-A boards, powered the way your team normally does it
  • CAN cables between the boards' CAN1 ports (CAN_H to CAN_H, CAN_L to CAN_L)
  • An ST-Link (SWD) to flash, and a 3.3 V USB-to-serial adapter to read USART6

9.3 Wiring checks

  • Termination. With everything powered off, measure the resistance between CAN_H and CAN_L. About 60 Ω (two 120 Ω resistors in parallel) is right. The Dev-A schematic shows a 120 Ω resistor next to each MCP2562 transceiver, so check how many are actually connected on your bus.
  • Serial. USART6 is TX = PG14, RX = PG9 on the MCU. Find which connector they go to in the Dev-A schematic. Connect adapter RX to board TX, adapter TX to board RX, and GND to GND. Open the port at 115200 baud, 8N1.

9.4 Flash each board

Each board gets its own file. With STM32CubeProgrammer's command-line tool:

STM32_Programmer_CLI -c port=SWD -w build/node1.elf -v -rst     # first board
STM32_Programmer_CLI -c port=SWD -w build/node2.elf -v -rst     # second board

You should see the same tx / rx lines as in the simulator, and the LEDs counting in binary.

This is what challenge 3 was preparing you for. All values are signed 16-bit, high byte first, at 1 Mbit/s. Always check the official manual for your motor and ESC (e.g. the C620 and GM6020 user guides); this table is a summary.

C620 / C610 ESCs (M3508, M2006 motors)

Watch out

Command ID 0x1FF is shared: C620 motors 5–8 and GM6020 motors 1–4 both listen to it. Two devices must never decode the same bytes on the same bus, so plan your motor IDs.

How the simulation is put together

sim/dev-a.repl describes one board: it starts from Renode's generic STM32F4 file and adds the parts this project uses (USART6, the 8 LEDs, the 180 MHz SysTick, the CAN init fix). sim/can_bus.resc builds the bus:

emulation CreateCANHub "canHub"

mach create "node1"
machine LoadPlatformDescription $ORIGIN/dev-a.repl
sysbus LoadELF $ORIGIN/../build/node1.elf
connector Connect sysbus.can1 canHub
showAnalyzer sysbus.usart6 Antmicro.Renode.Analyzers.LoggingUartAnalyzer
… (the same for node2 and node3)

Want a fourth board? Copy one block, call it node4, add 4 to NODES in the Makefile, and run make sim.
