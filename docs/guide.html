1What you'll build

On the robot, the main controller talks to the motors, the gimbal and the other boards over CAN. Before you touch a real robot, you'll learn CAN on three simulated RoboMaster Development Board Type A (“Dev-A”, STM32F427IIH6) boards.

Each board runs the same firmware. The only difference is a number, NODE_ID (1, 2 or 3). Every board:

  1. sends a small heartbeat frame on the bus at its own period, and
  2. prints every frame it receives on its serial port (USART6) and shows a counter from the frame in binary on its 8 LEDs.
BoardCAN ID it sendsPeriodData bytes
node10x101500 ms01, counter
node20x102600 ms02, counter
node30x103700 ms03, counter

Why a simulator?

Renode is an open-source simulator from Antmicro. It runs the exact .elf file you would flash onto a board, with the CPU, timers, GPIO, UART and CAN controller emulated. You can run three boards, connect them to one virtual bus and watch every frame without wiring anything or bricking a board.

Keep in mind

A simulator is not the real thing. Renode does not simulate wiring, pin choice, bit timing or bus errors. Chapter 8 lists exactly what changes on real boards. Read it before your first hardware session.

2CAN in ten minutes

2.1 One pair of wires, many boards

A CAN bus is two wires, CAN_H and CAN_L, usually twisted together. Every board connects to the same two wires, in parallel. A 120 Ω resistor at each end of the bus stops signals from reflecting back.

The bus only has two states:

  • Dominant = logic 0. A transmitter pushes CAN_H up and CAN_L down.
  • Recessive = logic 1. Nobody drives the bus; the resistors pull CAN_H and CAN_L to the same voltage.

If any one board sends a 0, the whole bus reads 0. “0 wins” is the most important rule in CAN; it makes arbitration and ACK work (see 2.5 and 2.6).

Because the receiver looks at the difference between the two wires, noise that hits both wires equally cancels out. That's why CAN survives next to motors.

2.2 Inside each board

  • The CAN controller lives inside the microcontroller. On the STM32F4 it's called bxCAN (there are two: CAN1 and CAN2). It builds frames, handles timing, CRC, ACK and retries, and filters incoming frames. Your code only ever talks to the controller, through the HAL.
  • The transceiver is a separate chip (an MCP2562 on the Dev-A). It converts the controller's TX/RX logic pins into CAN_H/CAN_L voltages and back.

bxCAN has 3 transmit mailboxes (frames waiting to go out), 2 receive FIFOs that hold 3 frames each, and 28 filter banks shared between CAN1 and CAN2.

2.4 Everyone hears everything

CAN has no addresses. When a board sends a frame, every other board on the bus receives it. The ID tells receivers what the message is about; each receiver decides whether it cares. The CAN controller can do that sorting in hardware with filters, so your code never sees frames it doesn't want. A board never receives its own frames.

2.5 IDs are priorities: arbitration

What if two boards start sending at the same moment? Both send their ID bit by bit, most significant bit first, and both listen to the bus while they send. Because 0 wins, as soon as one board sends a 1 but reads back a 0, it knows someone with a lower ID is also sending. It stops and tries again after the bus is free. The winner never notices and no data is lost.

Bit109876543210
node1 sends 0x10100100000001
node2 sends 0x1020010000001 ✗
bus00100000001

The lower the ID, the higher the priority. That's why DJI motor commands use ID 0x200 and the motors' feedback uses 0x201 and up.

2.6 ACK: somebody has to answer

In the ACK slot of every frame the sender transmits a 1, and every receiver that got the frame correctly overwrites it with a 0. If the sender reads back a 1, nobody received the frame. It reports an error and sends again, forever.

Common first-day bug

A board alone on the bus never gets an ACK, so its 3 transmit mailboxes fill up and stay full. Same if the other board isn't running, or uses a different bit rate. The firmware in this project prints tx skipped: all 3 mailboxes busy when that happens.

2.7 Bit rate and bit timing

All boards on a bus must use the same bit rate. RoboMaster robots use 1 Mbit/s, the rate DJI motors and ESCs expect. The controller splits each bit into small time slices called time quanta (tq) and reads the bus at the sample point, near the end of the bit:

Harmless warnings

At startup you'll see a few lines like WARNING … flash_controller: Unhandled write … ICEN and rcc: Unhandled write … RESERVED. They mean Renode doesn't model the flash cache or one reserved bit. Ignore them.

  • Which IDs does node1 receive? Does it ever receive 0x101? Why not?
  • The second data byte goes 00, 01, 02… for each board separately. Where does it come from?
  • node3 sends at 0.7 s, 1.4 s, 2.1 s. Which line of main.c decides that?

Renode has no picture of the board, but you can ask for any LED's state. While the simulation runs, type into the Renode prompt:

5.3 CAN1 settings and bit timing

static void MX_CAN1_Init(void)
{
  hcan1.Instance = CAN1;
  hcan1.Init.Prescaler = 3;
  hcan1.Init.Mode = CAN_MODE_NORMAL;
  hcan1.Init.SyncJumpWidth = CAN_SJW_1TQ;
  hcan1.Init.TimeSeg1 = CAN_BS1_11TQ;
  hcan1.Init.TimeSeg2 = CAN_BS2_3TQ;
  hcan1.Init.TimeTriggeredMode = DISABLE;
  hcan1.Init.AutoBusOff = ENABLE;
  hcan1.Init.AutoWakeUp = DISABLE;
  hcan1.Init.AutoRetransmission = ENABLE;
  hcan1.Init.ReceiveFifoLocked = DISABLE;
  hcan1.Init.TransmitFifoPriority = DISABLE;
  if (HAL_CAN_Init(&hcan1) != HAL_OK)
  {
    Error_Handler();
  }
}

The bit rate is set by three numbers:

bit rate = APB1 clock / Prescaler / (1 + BS1 + BS2)
         = 45 MHz     / 3         / (1 + 11 + 3)    = 1 000 000 bit/s
sample point = (1 + BS1) / (1 + BS1 + BS2) = 12 / 15 = 80 %
SettingWhat it does
ModeNORMAL talks to the bus. LOOPBACK sends frames to itself (handy for testing one board alone).
AutoBusOffIf too many errors happen the controller goes “bus-off” to protect the bus. ENABLE lets it recover on its own.
AutoRetransmissionResend a frame that wasn't acknowledged, or lost arbitration. Leave it on.
TransmitFifoPriorityDISABLE: when several mailboxes are full, the lowest ID goes first. ENABLE: oldest first.
If you change the clock

If APB1 is not 45 MHz, the bit rate is wrong and real boards stop talking to each other or to the motors. In CubeMX, the CAN1 parameter page shows the resulting “Baud Rate”; always check it says 1000000.

5.5 The filter: which frames do we keep?

static void CAN_Filter_Config(void)
{
  CAN_FilterTypeDef filter = {0};
  filter.FilterBank = 0;
  filter.FilterMode = CAN_FILTERMODE_IDMASK;
  filter.FilterScale = CAN_FILTERSCALE_32BIT;
  filter.FilterIdHigh = 0x0000;
  filter.FilterIdLow = 0x0000;
  filter.FilterMaskIdHigh = 0x0000;
  filter.FilterMaskIdLow = 0x0000;
  filter.FilterFIFOAssignment = CAN_FILTER_FIFO0;
  filter.FilterActivation = ENABLE;
  filter.SlaveStartFilterBank = 14;   /* banks 0-13 for CAN1, 14-27 for CAN2 */
  …
}

Until at least one filter is active, bxCAN throws every frame away, so you always need this. In mask mode, each mask bit says whether that ID bit matters:

  • mask bit 1 = “the received ID bit must equal the filter ID bit”
  • mask bit 0 = “don't care”

An all-zero mask means “don't care about anything”, so every frame is accepted into FIFO0. In exercise 3 you'll change this to accept only one ID.

5.6 Start the controller

CAN_Filter_Config();
if (HAL_CAN_Start(&hcan1) != HAL_OK) { Error_Handler(); }
/* Call HAL_CAN_RxFifo0MsgPendingCallback() whenever a frame arrives */
if (HAL_CAN_ActivateNotification(&hcan1, CAN_IT_RX_FIFO0_MSG_PENDING) != HAL_OK) { Error_Handler(); }

HAL_CAN_Init() leaves the controller in initialization mode, off the bus. HAL_CAN_Start() joins the bus. HAL_CAN_ActivateNotification() turns on the “frame received” interrupt.

5.7 Sending a frame

static void send_heartbeat(uint8_t counter)
{
  CAN_TxHeaderTypeDef header = {0};
  header.StdId = HEARTBEAT_ID;     /* 11-bit identifier */
  header.IDE = CAN_ID_STD;         /* standard (11-bit), not extended (29-bit) */
  header.RTR = CAN_RTR_DATA;       /* a data frame, not a remote request */
  header.DLC = 2;                  /* number of data bytes, 0..8 */
  header.TransmitGlobalTime = DISABLE;

  uint8_t data[2] = { NODE_ID, counter };
  uint32_t mailbox;

  if (HAL_CAN_GetTxMailboxesFreeLevel(&hcan1) == 0)
  {
    printf("[node%d] tx skipped: all 3 mailboxes busy\r\n", NODE_ID);
    return;
  }
  if (HAL_CAN_AddTxMessage(&hcan1, &header, data, &mailbox) != HAL_OK) { … }
  …
}

HAL_CAN_AddTxMessage() doesn't wait. It copies the frame into a free mailbox and returns; the controller sends it as soon as the bus is free and retries on its own if needed.

The main loop calls send_heartbeat() on a timer built from HAL_GetTick(), which counts milliseconds since boot (SysTick interrupt):

if ((int32_t)(HAL_GetTick() - next_tx) >= 0)
{
  next_tx += HEARTBEAT_PERIOD_MS;
  send_heartbeat(counter++);
}

Writing it as a subtraction keeps working when the 32-bit millisecond counter wraps around after 49 days.

5.8 Receiving a frame

When a frame passes the filter and lands in FIFO0, the CPU jumps to CAN1_RX0_IRQHandler(), which calls the HAL, which calls your callback:

void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *hcan)
{
  RxFrame *slot = &rx_queue[rx_head];
  if (HAL_CAN_GetRxMessage(hcan, CAN_RX_FIFO0, &slot->header, slot->data) != HAL_OK)
  {
    return;
  }

  uint32_t next = (rx_head + 1) % RX_QUEUE_LEN;
  if (next == rx_tail)
  {
    rx_dropped++;   /* queue full: this frame is lost */
    return;
  }
  rx_head = next;
}

The callback only copies the frame out of the hardware FIFO into our own queue. It does not print. Printing 40 characters at 115200 baud takes about 3.5 ms, and while an interrupt runs, other interrupts of the same or lower priority wait. On a robot that could mean missed motor feedback. Slow work belongs in the main loop:

RxFrame f;
while (rx_pop(&f))
{
  print_frame(&f);
  if (f.header.DLC >= 2)
  {
    show_on_leds(f.data[1]);
  }
}

rx_pop() switches interrupts off for a few instructions (__disable_irq() … __enable_irq()) so the callback can't change the queue halfway through a read. That short protected stretch is called a critical section.

5.9 LEDs

/* LED_A shows bit 0, LED_H shows bit 7. The LEDs are wired active-low:
 * writing 0 (RESET) to the pin turns the LED on. */
static void show_on_leds(uint8_t value)
{
  for (int bit = 0; bit < 8; bit++)
  {
    GPIO_PinState state = ((value >> bit) & 1U) ? GPIO_PIN_RESET : GPIO_PIN_SET;
    HAL_GPIO_WritePin(LED_GPIO_Port, LED_A_Pin << bit, state);
  }
}

On the Dev-A, each LED sits between 3.3 V (through a 1 kΩ resistor) and its pin, PG1–PG8. Current only flows, and the LED only lights, when the pin is low. That's called active-low, and it's why MX_GPIO_Init() sets the pins high first: all LEDs start off.

5.10 printf

printf() doesn't know about UARTs. The C library calls _write() to output characters, and main.c provides one that sends them out of USART6:

int _write(int file, char *ptr, int len)
{
  (void)file;
  HAL_UART_Transmit(&huart6, (uint8_t *)ptr, (uint16_t)len, HAL_MAX_DELAY);
  return len;
}

In the simulator, Renode prints whatever arrives on USART6 into its log; on a real board you'd read it with a USB-to-serial adapter (chapter 8).

6Exercises

Do them in order. After every change: save, run make sim (it rebuilds automatically), compare with the expected output, then quit. Solutions are in Appendix A; try first.

Undo everything

To get the original main.c back at any time: git checkout firmware/Core/Src/main.c. To keep your work but start fresh: git stash.

Exercise 1: Read the bus (no code)

Run make sim and answer, using only the log:

  1. At 1.4 s simulated time, which boards send and which receive?
  2. How many frames does node2 receive in the first 2 seconds? Predict first, then count.
  3. What is the last counter node1 has received at 1.85 s? Pause there and check its LEDs with gpioPortG.led_a State etc. Do they match the binary value?

Exercise 2: Send a 16-bit number

Goal: each heartbeat carries 4 bytes. Bytes 2 and 3 hold a 16-bit value, NODE_ID × 1000 + counter, high byte first (“big-endian”, the order DJI motors use). Receivers print the decoded value.

  1. In send_heartbeat(): set DLC to 4 and build a 4-byte data[]. Use value >> 8 for the high byte and value & 0xFF for the low byte.
  2. In print_frame(): if DLC >= 4, rebuild the value with (data[2] << 8) | data[3] and print it.

Expected:

[node1] tx id=0x101 dlc=4 value=1000
[node2] rx id=0x101 dlc=4 data: 01 00 03 E8  -> value=1000
[node3] rx id=0x101 dlc=4 data: 01 00 03 E8  -> value=1000
[node2] tx id=0x102 dlc=4 value=2000
[node1] rx id=0x102 dlc=4 data: 02 00 07 D0  -> value=2000

Think about it: 1000 is 0x03E8. What would the receiver print if it got the byte order backwards?

Exercise 3: Filters

Goal: every board accepts only ID 0x101 (node1's heartbeat). Change only CAN_Filter_Config().

In 32-bit mask mode, the 11-bit standard ID sits in the top 11 bits of the 32-bit filter register, so inside the 16-bit FilterIdHigh / FilterMaskIdHigh fields it's shifted left by 5:

Register bits31 … 2120 … 3210
MeaningSTID[10:0], the standard IDEXID (extended IDs only)IDERTR0
HAL fieldFilterIdHigh holds bits 31…16 and FilterIdLow holds bits 15…0, so the standard ID lands in bits 15…5 of FilterIdHigh.
  1. Set the filter ID to 0x101 (remember the shift).
  2. Set the mask so all 11 ID bits must match: 0x7FF, shifted the same way.

Expected: node1 receives nothing (it only hears others, and only 0x101 is allowed). node2 and node3 receive only 0x101:

[node1] tx id=0x101 dlc=2 data: 01 00
[node2] rx id=0x101 dlc=2 data: 01 00
[node3] rx id=0x101 dlc=2 data: 01 00
[node2] tx id=0x102 dlc=2 data: 02 00
[node3] tx id=0x103 dlc=2 data: 03 00
[node1] tx id=0x101 dlc=2 data: 01 01

Think about it: which mask accepts both 0x102 and 0x103 but nothing else? (Hint: they differ only in bit 0.)

Exercise 4: A DJI-style motor command

DJI's C620 motor controllers listen for ID 0x200: 8 bytes holding four signed 16-bit current commands, for motors 1 to 4, each high byte first (Appendix B). Let's fake it.

Goal:

  • node1 is the “main controller”. Right after each heartbeat it also sends ID 0x200 with the values 1000, -1000, 0, 0.
  • node2 pretends to be motor 1 (bytes 0–1) and node3 pretends to be motor 2 (bytes 2–3). Each decodes its own value and prints it.
  1. Write send_motor_command(int16_t m1, int16_t m2, int16_t m3, int16_t m4) next to send_heartbeat(), and add its prototype in the USER CODE PFP block.
  2. In the main loop, call it after send_heartbeat(), but only when NODE_ID == 1.
  3. In the receive loop: if the ID is 0x200 and this isn't node1, pick bytes 2 × (NODE_ID − 2) and the one after, combine them into an int16_t, and print it.

Expected:

[node2] rx id=0x200 dlc=8 data: 03 E8 FC 18 00 00 00 00
[node3] rx id=0x200 dlc=8 data: 03 E8 FC 18 00 00 00 00
[node2] my current command = 1000
[node3] my current command = -1000

Think about it: −1000 arrives as FC 18. Why? (Look up “two's complement”.) And why do the LEDs suddenly show 11101000 after a 0x200 frame?

8From the simulator to real boards

8.1 What the simulator does not check

Renode models CAN at the level of whole frames. Several things that break real buses are invisible in the simulator:

On real hardwareIn Renode
CAN1 must be on PD0/PD1 (the pins wired to the transceiver)Pin choice is ignored. PA11/PA12 would “work” too.
CAN1_RX needs a pull-upNot modeled
All boards must use the same bit rateBit timing is stored but ignored. A board at 500 kbit/s still “works”.
Someone must ACK; errors, retries and bus-off happenEvery frame succeeds instantly, even with no other board.
Arbitration takes time; a busy bus delays framesFrames are delivered instantly, no contention.
Wiring, termination, loose connectors, noiseNot modeled

The repository also works around one Renode quirk: ST's HAL_CAN_Init() requests initialization mode while the controller is still asleep, which real bxCAN allows and Renode's model didn't. A one-line hook in sim/dev-a.repl fixes that. You don't need it on hardware.

8.2 What you need

  • 2 or 3 Dev-A boards, powered the way your team normally does it
  • CAN cables between the boards' CAN1 ports (CAN_H to CAN_H, CAN_L to CAN_L)
  • An ST-Link (SWD) to flash, and a 3.3 V USB-to-serial adapter to read USART6

8.3 Wiring checks

  • Termination. With everything powered off, measure the resistance between CAN_H and CAN_L. About 60 Ω (two 120 Ω resistors in parallel) is right. The Dev-A schematic shows a 120 Ω resistor next to each MCP2562 transceiver, so check how many are actually connected on your bus.
  • Serial. USART6 is TX = PG14, RX = PG9 on the MCU. Find which connector they go to in the Dev-A schematic. Connect adapter RX to board TX, adapter TX to board RX, and GND to GND. Open the port at 115200 baud, 8N1.

8.4 Flash each board

Each board gets its own file. With STM32CubeProgrammer's command-line tool:

STM32_Programmer_CLI -c port=SWD -w build/node1.elf -v -rst     # first board
STM32_Programmer_CLI -c port=SWD -w build/node2.elf -v -rst     # second board

You should see the same tx / rx lines as in the simulator, and the LEDs counting in binary.

Exercise 2

In send_heartbeat():

In print_frame(), just before the final printf("\r\n"):

if (f->header.DLC >= 4)

Backwards byte order would turn 1000 (0x03E8) into 0xE803 = 59395.

filter.FilterIdHigh = 0x101 << 5;
filter.FilterIdLow = 0x0000;
filter.FilterMaskIdHigh = 0x7FF << 5;

To accept 0x102 and 0x103: ID 0x102 << 5, mask 0x7FE << 5 (bit 0 is “don't care”).

Exercise 4

Prototype, in USER CODE BEGIN PFP:

static void send_motor_command(int16_t m1, int16_t m2, int16_t m3, int16_t m4);

The function, in USER CODE BEGIN 4:

static void send_motor_command(int16_t m1, int16_t m2, int16_t m3, int16_t m4)
{
  CAN_TxHeaderTypeDef header = {0};
  header.StdId = 0x200;
  header.IDE = CAN_ID_STD;
  header.RTR = CAN_RTR_DATA;
  header.DLC = 8;
  uint8_t data[8] = { m1 >> 8, m1, m2 >> 8, m2, m3 >> 8, m3, m4 >> 8, m4 };
  uint32_t mailbox;
  HAL_CAN_AddTxMessage(&hcan1, &header, data, &mailbox);
}

The main loop, in USER CODE BEGIN 3:

if ((int32_t)(HAL_GetTick() - next_tx) >= 0)
{
  next_tx += HEARTBEAT_PERIOD_MS;
  send_heartbeat(counter++);
  if (NODE_ID == 1)
  {
    send_motor_command(1000, -1000, 0, 0);
  }
}

RxFrame f;
while (rx_pop(&f))
{
  print_frame(&f);
  if (f.header.StdId == 0x200 && NODE_ID != 1)
  {
    int slot = NODE_ID - 2;   /* node2 = motor 1 = bytes 0-1 */
    int16_t current = (int16_t)((f.data[2 * slot] << 8) | f.data[2 * slot + 1]);
    printf("[node%d] my current command = %d\r\n", NODE_ID, current);
  }
  if (f.header.DLC >= 2)
  {
    show_on_leds(f.data[1]);
  }
}

−1000 in 16-bit two's complement is 65536 − 1000 = 64536 = 0xFC18. The LEDs show data[1] of every frame, and in a 0x200 frame that's the low byte of motor 1's command, 0xE8 = 11101000.

BDJI motor CAN frames

This is what exercise 4 was preparing you for. All values are signed 16-bit, high byte first, at 1 Mbit/s. Always check the official manual for your motor and ESC (e.g. the C620 and GM6020 user guides); this table is a summary.

C620 / C610 ESCs (M3508, M2006 motors)

DirectionIDData
Command (you send)0x200bytes 0–1: motor 1 · 2–3: motor 2 · 4–5: motor 3 · 6–7: motor 4. C620 current command −16384…16384 (about −20…20 A).
Command (you send)0x1FFthe same layout for motors 5–8
Feedback (motor sends)0x200 + motor ID
(0x201–0x208)		bytes 0–1: rotor angle 0…8191 (= 0…360°) · 2–3: speed in rpm · 4–5: actual torque current · 6: temperature °C (C620) · 7: unused

GM6020 gimbal motor

DirectionIDData
Command0x1FF / 0x2FFfour voltage commands (−30000…30000) for motor IDs 1–4 / 5–7
Feedback0x204 + motor IDsame layout as the C620 feedback
Watch out

Command ID 0x1FF is shared: C620 motors 5–8 and GM6020 motors 1–4 both listen to it. Two devices must never decode the same bytes on the same bus, so plan your motor IDs.

Reading feedback is exactly the decoding you did in exercises 2 and 4: check the ID, then combine two bytes into an int16_t.

How the simulation is put together

sim/dev-a.repl describes one board: it starts from Renode's generic STM32F4 file and adds the parts this project uses (USART6, the 8 LEDs, the 180 MHz SysTick, the CAN init fix). sim/can_bus.resc builds the bus:

emulation CreateCANHub "canHub"

mach create "node1"
machine LoadPlatformDescription $ORIGIN/dev-a.repl
sysbus LoadELF $ORIGIN/../build/node1.elf
connector Connect sysbus.can1 canHub
showAnalyzer sysbus.usart6 Antmicro.Renode.Analyzers.LoggingUartAnalyzer
… (the same for node2 and node3)

Want a fourth board? Copy one block, call it node4, add 4 to NODES in the Makefile, and run make sim.
